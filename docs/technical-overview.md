# BIM-AI Studio 技术说明

> 本文基于当前仓库目录与实现状态编写，描述系统解决的问题、总体架构、模型调用工具的完整链路，以及技术可扩展性的边界。

---

## 1. 摘要

BIM-AI Studio 是一套把**外部智能模型**与 **BIM 几何内核**连接起来的本地中间层。它不训练模型，也不实现几何算法，而是解决两者之间的工程断裂：

> 模型能生成意图，但不能直接、安全、可复现地修改建筑模型；
> 内核能执行操作，但不理解自然语言，也不具备事务与审计语义。

系统的做法是把内核能力**收敛为一组类型化工具**，让模型只能通过工具名与结构化参数表达动作，由宿主统一处理线程、事务、回滚与读回。

---

## 2. 问题定义

### 2.1 线程亲和性

Revit API 的对象模型具有线程亲和性，绝大多数读写必须在应用主线程完成。模型的推理循环通常运行在独立线程或独立进程，二者之间存在调度断层。

### 2.2 动作空间的可审计性

若允许模型直接生成并执行任意代码，每次修改都缺乏稳定的语义边界：难以复现、难以比对、难以在失败时精确回滚。

### 2.3 写入的一致性与可观测性

一次建模操作往往涉及多个图元。缺乏事务边界时，部分成功会造成难以察觉的模型污染。

### 2.4 工具集合的异质性

不同工作站、不同版本的插件提供的工具集合不同。把工具清单静态写入提示词，会导致调用与实现错位。

### 2.5 结论

上述四点共同指向一个设计约束：**模型的动作空间必须是有限、可枚举、可校验的**。这正是工具层存在的理由。

## 3. 仓库划分

系统按“工具层 / 应用层”拆为两个仓库，边界是工具契约。

| 仓库 | 职责 | 关键目录 |
| --- | --- | --- |
| `BIM-AI-Studio` | 工具契约、注册表、服务层、120 个工具源码 | `toolset/`、`src/ReVitAI.Bridge/`、`agent/revit-2027/` |
| `BIM-AI-Studio-App` | 加载入口、上层界面、模型接入、PDF 处理 | `host/hybrid-ui/` |

应用层通过 git submodule 引用工具层源码，不依赖预编译产物。

## 4. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 表达层   自然语言 / 结构化调用                                  │
│          · 内置 Agent（进程内）                                 │
│          · Codex / MCP 客户端（进程外）                          │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 传输层   Named Pipe（当前用户） / 进程内调用                     │
│          · discovery 文件：pipeName + processId                 │
│          · 单行 JSON 请求 / 单行 JSON 响应                      │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 调度层   工具注册表 → 调用处理器 → ExternalEvent                 │
│          · 参数注入、工具查找、线程封送                          │
│          · 事务开始 / 提交 / 回滚、失败预处理                    │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 执行层   服务层 → BIM 内核 API                                  │
│          · 唯一直接操作内核对象的代码区                          │
│          · 单位换算、ID 解析、几何构造、读回                     │
└──────────────────────────────────────────────────────────────┘
```

层的职责是单向的：上层只能通过下层暴露的契约调用，不能反向持有内核对象。

## 5. 工具契约

### 5.1 接口

```csharp
public interface IAITool
{
    string Name { get; }
    string Description { get; }
    string Category { get; }
    string ParametersSchema { get; }   // JSON Schema 字符串
    Task<AIToolResult> ExecuteAsync(AIToolContext context, CancellationToken ct = default);
}
```

### 5.2 元数据

```csharp
[AITool("create_straight_wall",
        Category = "元素创建",
        Description = "在指定标高处创建直墙。所有距离单位为毫米",
        RequiresTransaction = true,
        RequiresModification = true)]
```

四个开关决定执行路径：

| 开关 | 语义 |
| --- | --- |
| `RequiresTransaction` | 需要回主线程并包于单一事务 |
| `RequiresModification` | 会改变模型状态 |
| `RequiresActiveDocument` | 执行前校验活动文档 |

### 5.3 结果

```csharp
public sealed class AIToolResult
{
    bool Success;
    string Message;   // 自然语言摘要
    object Data;      // 结构化载荷：标识、计数、失败明细
    string Error;     // 可定位的失败原因
}
```

写入类工具的成功判据是**读回一致**，而不是“未抛出异常”。

### 5.4 注册与发现

注册表在首次调用时扫描程序集，条件为：类、非抽象、实现 `IAITool`、带 `[AITool]`。实例化时按构造函数参数类型注入服务，解析失败则跳过并记录，不中断宿主启动。

## 6. 执行模型

### 6.1 线程封送

```
调用线程                      Revit 主线程
   │                              │
   ├─ TaskCompletionSource ───────┤
   ├─ ExternalEvent.Raise() ─────▶│ Execute(UIApplication)
   │                              ├─ Transaction.Start()
   │                              ├─ 工具执行
   │                              ├─ Regenerate + Commit / Rollback
   │◀──── SetResult ──────────────┤
   ▼
 await 结果
```

### 6.2 事务生命周期

由宿主统一管理，工具内部不得自行开启事务：

```
Start → Execute → (Success ? Regenerate + Commit : RollBack) → Result
```

失败处理器只删除警告、不改写错误，避免批量建模时弹窗打断执行。

### 6.3 串行化

单个宿主进程只暴露一个事件槽位，请求串行处理。并发写入被显式拒绝，而不是排队重试。

## 7. 外部模型如何调用内置工具

系统支持两条调用路径，工具契约完全相同。

### 7.1 能力下发

工具定义在运行时由注册表生成，不写死在提示词里：

```json
{
  "type": "function",
  "function": {
    "name": "create_straight_wall",
    "description": "在指定标高处创建直墙。所有距离单位为毫米",
    "parameters": { "type": "object", "properties": { }, "required": [] }
  }
}
```

每次请求前重新生成 `tools` 数组，因此设备间工具数量不同也不会错位。

### 7.2 进程内路径：内置 Agent

```
用户输入
   │
   ▼
AgentLoop
   ├─ 组装 system + 历史 + tools
   ├─ 调用模型（chat/completions，当前实现为非流式）
   ├─ 若返回 tool_calls：
   │     ├─ 逐个 IToolInvoker.InvokeAsync
   │     ├─ 结果作为 role=tool 消息回填
   │     └─ 再次请求模型
   └─ 模型不再请求工具 → 输出最终答复
```

关键点：

- 工具通过 `IToolInvoker` 抽象调用，界面不直接持有内核对象；
- 工具执行结果必须回填给模型，模型才能基于真实结果继续推理；
- 当前客户端以 `stream = false` 请求，界面通过 `chat.progress` / `chat.toolResults` 事件展示每步进度，而不是逐 token 流式渲染。

### 7.3 进程外路径：Codex / MCP

```
Codex / MCP client
   │  读取可用的 bridge discovery 文件
   ▼
Named Pipe（当前用户）
   │  {"type":"invoke","tool":"...","arguments":{...}}
   ▼
ToolDispatcher / Registry
   │
   ├─ 只读工具：直接执行
   └─ 写入工具：ExternalEvent → Transaction
   ▼
{"type":"invoke","success":true,"payload":{...}}
```

支持 `ping`、`tools.list`、`invoke` 三类请求，均为单行 JSON。

### 7.4 一次工具调用的完整往返

```jsonc
// 1. 模型返回工具调用
{ "tool_calls": [ { "id": "call_1", "type": "function",
    "function": { "name": "create_straight_wall",
                  "arguments": "{\"start_x\":0,\"start_y\":0,\"end_x\":6000,\"end_y\":0,\"level_id\":311,\"wall_type_id\":398}" } } ] }

// 2. 宿主执行并读回
{ "wall_id": 339672, "level_id": 311 }

// 3. 回填给模型
{ "role": "tool", "tool_call_id": "call_1",
  "content": "{\"success\":true,\"message\":\"成功创建墙体，ID: 339672\",\"data\":{\"wall_id\":339672}}" }
```

### 7.5 为什么不让模型直接写代码

| 直接执行代码 | 工具契约 |
| --- | --- |
| 动作空间无限 | 有限、可枚举 |
| 难以复现 | 工具名 + 参数可复现 |
| 难以校验 | Schema 校验 |
| 难以回滚 | 统一事务 |
| 无法审计 | 调用日志可追溯 |

## 8. 技术可扩展性

### 8.1 新增工具

成本三处：工具类元数据、`ExecuteAsync` 实现、可选的服务方法。调度层、传输层、事务层无需改动。

工具名即契约标识，发布后视为稳定接口；破坏性变更须以新工具名引入。

### 8.2 新增模型

修改 `ApiUrl` 与 `Model` 即可。请求遵循 OpenAI Chat Completions 形式，工具数组与调用协议不变。

### 8.3 新增界面

界面只依赖两类契约：工具调用接口与消息协议。已有实现是 DockablePane + WebView2，但其结构可整体替换（原生 WPF、外置窗口、Web 前端均可）。

### 8.4 新增传输方式

`IToolInvoker` 与桥接层均为抽象，新增 HTTP、gRPC 或消息队列只需实现同一接口，工具层无感知。

### 8.5 扩展瓶颈

| 瓶颈 | 原因 | 缓解方向 |
| --- | --- | --- |
| 单事件槽串行 | Revit 主线程模型 | 分批提交、减少单次调用粒度 |
| 单文档 | 未验证多文档并发 | 引入文档上下文标识 |
| 非流式响应 | 当前客户端一次请求一次响应 | 增加 SSE 解析与增量渲染 |
| Schema 手写 | 工具契约以字符串声明 | 由生成器产出并校验 |
| 依赖集合 | 多数依赖已迁移为 NuGet 包 | 新增依赖必须进入许可审计 |

## 9. 非功能属性

| 属性 | 设计选择 |
| --- | --- |
| 可审计 | 动作空间有限，调用有名称、参数、结果与耗时 |
| 可回滚 | 单次调用对应单一事务，失败即回滚 |
| 可验证 | 写入后强制读回，返回真实标识 |
| 可移植 | 命名管道，不依赖网络与外部服务 |
| 安全性 | 当前用户作用域、无端口、无任意代码执行入口 |

## 11. 小结

BIM-AI Studio 的核心不是“让模型生成更多操作”，而是**把模型的操作能力约束为一个可枚举、可校验、可回滚的契约集合**。

工具是契约的实例，注册表是契约的目录，事务是契约的执行语义，读回是契约的验收条件。外部模型无论以何种方式接入，都只在这套契约上工作——这正是系统可扩展、可审计、可替换的根本原因。

# BIM-AI Studio 开发说明

> 面向开发者与架构评审。描述系统要解决的问题、能力边界、扩展机制与底层契约。

---

## 1. 问题定义

在建筑信息模型（BIM）软件中引入生成式智能体，存在四类结构性障碍。

**其一，执行环境的线程约束。** Revit 的 API 对象模型具有线程亲和性，绝大多数读写操作必须在应用主线程完成。而智能体的推理循环通常运行在独立线程或进程，二者之间存在天然的调度断层。

**其二，动作空间的可审计性。** 若允许智能体直接生成并执行任意代码，则每一次模型修改都缺乏稳定的语义边界：难以复现、难以比对、难以在失败时精确回滚。

**其三，写入的一致性与可观测性。** 建筑模型中的一次操作往往涉及多个图元及其参数。缺乏事务边界时，部分成功会造成难以察觉的模型污染。

**其四，工具集合的异质性。** 不同工作站、不同插件版本所提供的工具集合并不一致。将工具清单静态写入提示词，会导致调用与实现错位。

本系统将上述问题收敛为一个命题：**在智能体与几何内核之间，建立一层受约束、可枚举、可验证的类型化工具契约。**

---

## 2. 系统模型

系统采用四层结构，层间仅通过显式契约耦合。

```
表达层  Agent / MCP client / script
   │        JSON request（tool, arguments）
   ▼
传输层  Named Pipe（current-user） + discovery file
   │
   ▼
调度层  Tool registry → invocation handler → ExternalEvent
   │        事务边界、失败预处理、结果封装
   ▼
执行层  Service layer → Revit API
```

**表达层**只负责意图表达，不持有任何内核对象；**传输层**为单用户命名管道，不开放网络端口；**调度层**承担线程封送与事务生命周期；**执行层**是唯一直接操作内核对象的代码区。

这种划分使智能体的输出被限制为「工具名 + 结构化参数」，而非任意程序文本。动作空间因此成为有限集合，可被枚举、校验与审计。

## 3. 能力域

工具按能力域组织，域内工具共享同一组服务依赖。

| 能力域 | 内容 | 典型操作 |
| --- | --- | --- |
| 上下文感知 | 文档、视图、单位、模型概览 | 读取活动文档、单位制、可见范围 |
| 基准体系 | 标高、轴网 | 创建与查询标高、网格线 |
| 建筑构件 | 墙、楼板、柱、梁、门窗、房间 | 参数化创建、类型解析、宿主关系 |
| 注释与详图 | 详图线、文字、尺寸、标记 | 视图内二维绘制与标注 |
| 视图与表达 | 平面/三维视图、裁剪、显示样式 | 视图创建、激活、导出 |
| 参数与数据 | 参数读写、共享参数、明细表 | 批量赋值、结构化查询 |
| 几何分析 | 位置、包围盒、几何提取、碰撞 | 读回校验与空间分析 |
| 批量与规划 | 批量执行、分阶段绘图计划 | 依赖排序、统一撤销组 |

能力域之间保持单向依赖：构件依赖基准体系，注释依赖视图，规划层依赖其余各域。该偏序关系同时是建模的推荐执行顺序。

## 4. 扩展机制

工具集合通过**声明式注册 + 反射装配**扩展，而非修改调度核心。

### 4.1 注册单元

一个工具是一个实现 `IAITool` 的类，并以 `[AITool]` 声明元数据：

```csharp
[AITool("create_straight_wall",
        Category = "元素创建",
        Description = "在指定标高处创建直墙。所有距离单位为毫米",
        RequiresTransaction = true,
        RequiresModification = true)]
public sealed class CreateStraightWallTool : IAITool { ... }
```

注册表在首次调用时扫描程序集，条件为：类型为类、非抽象、实现 `IAITool`、且带 `[AITool]`。满足条件者按构造函数参数类型注入服务，注入失败则跳过并记录，不中断宿主启动。

### 4.2 扩展成本

新增一个工具需要且仅需要三处改动：

1. 在工具类中声明名称、分类、描述与参数 Schema；
2. 在 `ExecuteAsync` 中读取参数、调用服务、构造结果；
3. 在能力域内补充对应的服务方法（若已有同类服务则无需新增）。

调度层、传输层与事务层无需改动。工具名称即注册键，亦是对外契约的稳定标识。

### 4.3 契约稳定性

工具名称一经发布视为稳定接口。参数只允许向后兼容的扩展（新增可选字段），不允许改变既有字段的语义或单位。破坏性变更须通过新工具名引入，旧名保留一个发布周期。

## 5. 底层契约

### 5.1 工具接口

```csharp
public interface IAITool
{
    string Name { get; }
    string Description { get; }
    string Category { get; }
    string ParametersSchema { get; }
    Task<AIToolResult> ExecuteAsync(AIToolContext context, CancellationToken ct = default);
}
```

### 5.2 执行语义

调度层依据元数据决定执行路径：

| 元数据 | 语义 |
| --- | --- |
| `RequiresTransaction = false` | 只读操作，可在调用线程直接执行 |
| `RequiresTransaction = true` | 需在应用主线程执行，并包于单一事务 |
| `RequiresModification = true` | 会改变模型状态，须经事务与读回 |
| `RequiresActiveDocument = true` | 执行前校验活动文档存在 |

事务的生命周期由宿主统一管理：

```
Start → Execute → (Success ? Regenerate + Commit : RollBack) → Result
```

工具实现内部不得自行开启事务。该约束保证批量调用时的原子性，并避免嵌套事务导致的半提交。

### 5.3 参数契约

参数以 JSON Schema 描述，遵循最小子集：`type`、`properties`、`required`。约定如下：

- 长度类入参以毫米为公开口径，进入执行层后统一换算为内核单位；
- 标识类入参（标高、类型、视图）不得使用默认值兜底，必须显式解析并在失配时报错；
- 同一工具若同时支持单条与批量形式，批量字段存在时优先，且结果须同时给出请求数、成功数与失败明细。

### 5.4 结果契约

```csharp
public sealed class AIToolResult
{
    bool Success;
    string Message;   // 面向人与模型的自然语言摘要
    object Data;      // 面向程序的结构化载荷：标识、计数、失败项
    string Error;     // 可定位的失败原因
}
```

写入类工具的成功判据不是「未抛出异常」，而是**读回一致**：创建返回的标识必须在同一文档中可解析，且关键属性与请求值相符。

### 5.5 传输契约

传输层采用单行 JSON 请求 / 单行 JSON 响应。请求类型限于 `ping`、`tools.list`、`invoke`。宿主在启动时写入发现文件（管道名与进程标识），退出时删除；调用方须校验进程存活后再连接。

同一宿主进程仅暴露一个事件槽位，请求串行处理。并发写入被显式拒绝，而非排队重试，以避免模型状态的不确定合并。

## 6. 非功能属性

| 属性 | 设计选择 |
| --- | --- |
| 可审计性 | 动作空间有限；每次调用有名称、参数、结果与耗时 |
| 可回滚性 | 单次调用对应单一事务，失败即回滚 |
| 可验证性 | 写入后强制读回，结果携带真实标识 |
| 可扩展性 | 注册表反射装配，新增工具不改核心 |
| 可移植性 | 传输层为命名管道，不依赖网络与外部服务 |
| 安全性 | 当前用户作用域、无端口、无任意代码执行入口 |

---

## 7. 边界与假设

- 仅支持单文档会话；多文档并发未验证。
- 依赖本地安装的几何内核 API，不随仓库分发其二进制。
- 不承担模型语义正确性（如构造合理性）的判断，该职责属于调用方与设计规范。
- 工具层源代码中不包含账户、计费、更新等业务模块；这些能力不属于工具契约。

---

## 8. 小结

本系统的核心不在于「让模型生成更多操作」，而在于**把模型的操作能力约束为一个可枚举、可校验、可回滚的契约集合**。工具是契约的实例，注册表是契约的目录，事务是契约的执行语义，读回是契约的验收条件。

在此意义上，扩展工具名单不是增加代码量，而是扩展契约的覆盖面；工具编写的质量，取决于契约描述的精确程度。
